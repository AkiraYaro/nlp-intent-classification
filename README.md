# nlp-intent-classification

# Классификация интентов в диалогах банковской поддержки

Тестовое задание: сгенерировать синтетический датасет диалогов клиента с поддержкой банка
и обучить энкодер-модель определять тему последней реплики клиента с учётом контекста диалога.

# Пример:
# 1
user: Здравствуйте

A: Здравствуйте! Чем можем помочь?

user: Я вчера отправил 30 тысяч маме, деньги до сих пор не дошли

Class: transfer_status (классифицируем тему обращения как статус перевода)

# 2
user: хочу открыть вклад на 200 тысяч на год

A: Отлично, могу оформить накопительный счёт прямо сейчас, подтверждаете?

user: да, давайте

Class: deposit_open (классифицируем тему обращения как открытие вклада)

## Содержимое

- `shift_intent_nlp_task.ipynb` — ноутбук с обеими частями задачи и результатами выполнения
- `train.json`, `test.json` — сгенерированный датасет

## Данные

16 классов банковской тематики: переводы (статус, отмена, комиссия, лимиты), карты (блокировка,
доставка, ПИН), кредиты (оформление, ставки, досрочное погашение, график платежей), вклады
(открытие, ставки), выписка по счёту, проблемы с приложением, мошенничество. Часть классов
намеренно сделана близкими по смыслу, чтобы задача не решалась по одному ключевому слову.

Генератор — `Qwen/Qwen2.5-7B-Instruct-AWQ` через vLLM. Итого 400 диалогов в обучающей выборке
(25 на класс) и 192 в тестовой (12 на класс).

Половина диалогов генерировалась в режиме, где последняя реплика клиента короткая и сама по себе
непонятна («да, давайте», «а когда приедет курьер?») — тему можно определить только из контекста.

Тестовая выборка генерировалась ОТДЕЛЬНЫМ прогоном с ДРУГИМИ описаниями стиля клиента.
Дополнительно из неё исключены диалоги, чья последняя реплика дословно встречается в обучающей.

### Валидация сгенерированного

Небольшая модель часто уходит от темы и ломает формат, поэтому каждый диалог проходит проверку:

- в тексте должна звучать тема класса (список ключевых слов);
- если последняя реплика короткая, тему обязана задавать одна из предыдущих реплик клиента;
- последняя реплика — вопрос или согласие, а не благодарность и не прощание;
- один и тот же вопрос не может принадлежать двум разным классам;
- дубликаты удаляются.

## Классификатор

В модель подаётся весь диалог. При превышении максимальной длины обрезается его начало
(`truncation_side="left"`), чтобы последняя реплика клиента гарантированно осталась на входе.

| Модель | accuracy | macro-F1 |
|---|---|---|
| ruBert-base, весь диалог | 0.964 | 0.963 |
| TF-IDF + LogReg, весь диалог | 0.958 | 0.959 |
| rubert-tiny2, весь диалог | 0.943 | 0.942 |
| rubert-tiny2, только последняя реплика | 0.359 | 0.331 |
| TF-IDF + LogReg, только последняя реплика | 0.292 | — |

## Выводы

**Контекст решает.** При обучении только на последней реплике качество падает с 0.94 до 0.36.
Это подтверждает, что датасет собран в соответствии с условием задачи, а модель действительно
опирается на контекст, а не на одну фразу. В демонстрации это видно напрямую: одна и та же
реплика «да, давайте» классифицируется как `card_block` в одном случае или `deposit_open` в другом, в зависимости
от предыдущих сообщений.

**Разница между моделями невелика.** ruBert-base выигрывает у rubert-tiny2 около двух пунктов,
но это четыре диалога (выигрыш всего 2%) на тесте из 192, и разброс между запусками с разными seed сопоставим
с этой разницей. При этом tiny2 обучается за 13 секунд против 75 и весит в шесть раз меньше —
для сервиса с высокой нагрузкой это может быть важнее двух пунктов метрики.

**Бейзлайн подозрительно силён.** TF-IDF (term frequency – inverse document frequency) + логистическая регрессия даёт 0.958, практически
наравне с трансформерами. Это говорит о том, что синтетический датасет хорошо различим
по лексике: LLM пишет «идеальных» клиентов, которые называют тему прямо. Фильтрация
по ключевым словам дополнительно усилила этот эффект. На реальных диалогах с разговорной
речью и опечатками преимущество трансформеров должно проявиться заметнее.

**Основные ошибки — между близкими классами.** `transfer_cancel` путается с `transfer_status`,
`deposit_open` с `deposit_rates`. Это семантически смежные темы, где граница не всегда очевидна
и человеку.

## Что можно улучшить

- Добавить классы `smalltalk` и `other`: сейчас любое сообщение, не подходящее по смыслу ни одной из 16 тем, модель обязана
  отнести хоть к какой-то из этих тем.
  В системе нужен fallback (запасной вариант) по порогу уверенности.
  Если уверенность ниже порога (скажем, 0.5), не выдавать заготовленный ответ, а передать диалог живому оператору. Отдельный класс other в датасете нужен, чтобы модель училась узнавать «не наша тема», а не угадывала.
- Усреднить метрики по нескольким seed вместо одного запуска.
- Увеличить датасет и разнообразие формулировок, чтобы снизить различимость классов
  по отдельным словам.
